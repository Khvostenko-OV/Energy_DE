# Unit identity: reference_id in staging, serial key in core, freshness-gated updates

Staging identity derives from `reference_id` (canonicalized `energy_source` + `reference_id`); the 39 solar rows without a `reference_id` get a synthetic hash from source + x/y + installed_capacity + commissioning date, and that synthetic identity exists **only in staging** — core replaces it with a serial integer `unit_id`. Core therefore carries no natural key as its identity; it keeps a data-integrity unique index on `(energy_source, reference_id)` where `reference_id` is present, but that index is not the update key.

Incremental loads match an incoming staging row to core by its record identity — `reference_id` when present, the synthetic hash otherwise — and apply a freshness gate: if the incoming `reference_date` is fresher, `UPDATE` the matched row in place (surrogate `unit_id` stays stable, dimensional property links are refreshed); if not fresher, skip; if unmatched, insert. Geometry is carried as data and reserved for the load-stage collision checks, not identity.

The spec v2 update key is `reference_id` + `reference_date`, so identity and provenance stay coupled to the record id (unique across all sources per data inspection); the freshness gate is what keeps a staler re-ingestion from clobbering newer state. Rejected delete+insert-on-update (regenerates `unit_id`, orphaning property links and admin bookkeeping) and upstream-removal detection (v2 has no such mechanism).
