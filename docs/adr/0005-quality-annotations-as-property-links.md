# Quality annotations are boolean flags plus property links, not a quality register

Transform-level quality failures set a staging `bad_quality` boolean and write a property link `(name='bad_quality', value='\n'.join(failed-check descriptions))` through `units_properties`; only good records are inserted into core. Load-level collisions set a core `collision` boolean and write descriptive property links (`collision`, and `close_to` naming the neighbouring unit's id). The normalized dimension tables are named `properties` / `units_properties` (renamed from `parameters` / `units_parameters`), and the raw/staging jsonb bag of secondary attributes was renamed from `properties` to `secondary_attributes` to stop the column and the table colliding on the same word.

The spec's "add property 'bad_record' / 'collision' / 'close_to'" language is satisfied by the normalized property links, which keeps one audit trail per unit queryable alongside its attributes, with the booleans as cheap filters. Rejected the v1 `quality_checks` register plus `has_quality_issues` boolean (a second bookkeeping system the property links already cover) and rejected adding jsonb to core to hold the annotations literally. `geo_accuracy=2` is deliberately not a flagged collision; synthetic identities are staging-only and not flagged in core.
